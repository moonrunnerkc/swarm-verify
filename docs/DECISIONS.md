# Decisions

Open choices made while building Swarm Verify, dated, with the reason. Append only.

## 2026-10-31: ownership

- This repository becomes the verifier's source home (ADR 0015 in Swarm Orchestrator). Until the source moves in, the README says so and the Action keeps installing the published 1.3.1.
- `AGENTS.md` is a link to `CLAUDE.md`, as in the orchestrator, so both agent conventions read one file.

## 2026-10-31: the source moves here

- History came from swarm-orchestrator by `git filter-repo` on a scratch clone, keeping the verifier's paths, then a merge with unrelated histories into this repository: 151 commits since the 2026-10-28 rebuild. Earlier history was under other paths and stays in the orchestrator and its archive.
- The signed predicate is the result model: the API result is the predicate plus integrity, evidence paths and failure output. One typed result model, so the signed record and what callers read cannot disagree. The predicate type becomes `https://github.com/moonrunnerkc/swarm-verify/result/v1`; `verdict/v1` is retired with its `pass`, `fail`, `unmeasured` vocabulary.
- A request with no requirements yields `scope: regression-only`, stated in the text report, so a pass of a pull request without declared requirements is never read as task acceptance.
- No declared or detected checks is `blocked`, not `unmeasured`: a missing prerequisite, not a property of the change.
- Requesting isolated execution is `blocked` until the container backend exists, rather than silently running on the host. Host runs say `host, not isolated` and report an open network.
- Exit codes: 0 complete, 1 failed, 4 unverified or unresolved, 5 blocked; the offline checker uses 6 for an integrity failure and 1 for a valid but not-complete result, so integrity and acceptance never share a zero.
- verify.mjs re-derives the recorded state from the recorded evidence with the same rule; a recorded `complete` that the evidence does not support is an integrity failure.
- The first requirement evaluator maps named tests, named checks and structural claims to statuses; kind-specific witnesses (fail before and pass after, preserved behavior, resolved versions) follow with per-test identities.
- `dependencies: "prepare"` runs the base's declared setup command or the install its lockfile asks for (npm ci, pnpm, yarn, bun, uv sync --frozen); `linked` keeps the old behavior and is never reproducible.
- The Action builds the verifier from this repository at the workflow's ref (`npm ci`, `npm run build`) instead of installing a published version, so `@v2` runs the source at that tag. The 1.x Action reference, the fork example and the recorded demos described commands 2.0 does not have and were removed; they remain in 1.x history.
- Released changelog sections are not path-checked here: they describe releases built from swarm-orchestrator's tree.
- The changelog's `2.0.0 - 2026-10-29` section was tagged `swarm-verify-v2.0.0` in swarm-orchestrator and never reached npm (its release job failed). That tag is left where it is; 2.0.0 will be released from this repository, and its changelog section is rewritten at release to cover what ships.
- devDependencies resolved fresh (biome 2.6.4); biome.json migrated to its schema.

## 2026-10-31: verification semantics

- The eleven review probes are split by where their behavior lives: eight are verifier tests (src/probes/probes.integration.test.ts), and the three that need the agent loop (the empty `double(n)` completion, a correct edit on the last step, a stale attestation) are orchestrator tests. All eight verifier probes failed against the code before this change; the run log records each observation.
- The ignored `.swarm` failure reproduces on git 2.54.0 (Apple Git-157) as on 2.51.1.
- `node --test` reporters go in through `NODE_OPTIONS`, because flags placed after a positional test path are read as file patterns and npm script forwarding appends there. A command with two `node --test` runs is not read test by test, since both would write one report.
- One run model replaces protected paths: obligation (base tests against candidate source), candidate (as delivered), witness (candidate tests against base source). The obligation run happens only when the candidate modified or deleted test files and the witness run only when it added or rewrote some, so a source-only change still costs one candidate run.
- "Removed" blocks: a test file the candidate deleted takes its base tests with it, even when their originals still pass against the candidate, because the delivered tree no longer carries them.
- A check whose collected tests all fail at both commits is `unresolved`, not `inherited-failures`: nothing in it tells the candidate from no change. Zero collected is `no-tests`.
- Relocation is "identical after removing import statements and blank lines", a deterministic rule; a move that also edits test bodies is read as a delete and an add, which blocks, and is listed as a limitation.
- TypeScript mutants are checked with Node's built-in `stripTypeScriptTypes` in transform mode, since `node --check` exits 0 on a broken `.ts` file; JSX and TSX lines are not mutated because nothing here parses them.
- Held-out runs restore only test-category files to the base (not lockfiles or manifests), so an upgrade is judged by the held-out checks on its own dependencies.
- `scripts/check-caps.mjs` enforces the 300-line file cap here, as in the orchestrator.

## 2026-10-31: offline re-derivation

- verify.mjs re-derives a complete state with the same kind rules as src/verify/requirements.ts. The rule is written twice (TypeScript and the dependency-free checker) because the checker must run with nothing installed; allowed-changes.integration.test.ts runs the checker on every complete result so the two cannot drift silently.

## 2026-10-31: execution trust

- Docker is the one isolated backend, used through its CLI; there is no backend abstraction. Images: `node:24` and `ghcr.io/astral-sh/uv:python3.12-bookworm`, pinned by their multi-architecture index digests (both resolved to arm64 on the development machine), chosen by whether the base has a package.json. A request may name its own image.
- Pulling a missing image happens in the verifier before any check, as part of preparing the execution environment; the image's content digest goes into the environment identity.
- The scratch directory of an isolated verification lives under `$SWARM_HOME/work`: colima and Docker Desktop share the user's home with their VM and not `/var/folders`, so a mount from the system temporary directory fails with "bind source path does not exist" (observed on colima 2026-10-31).
- The container runs as the invoking user's uid and gid, so files it writes into the scratch directory can be removed by the verifier on Linux; on colima the mapping is the same.
- The judge's code is written once per verification and never replaced: replacing it between runs made the file read as missing inside the next container through colima's shared filesystem (observed: ENOENT for judge.mjs on the second run). Its reports moved to `judge-reports/` so the judge directory can be mounted read-only.
- In isolation, a Python project without uv.lock is resolved with `uv lock` during the dependency stage and the generated lock's digest is recorded; with uv.lock it is `uv sync --frozen --all-extras`. pnpm and yarn go through corepack, which may fetch the manager during that same stage.
- A dependency cache under the verifier's home is mounted only during the dependency stage. Its entries are content-addressed by the package managers, so a candidate's install scripts cannot substitute bytes another lockfile resolves.
- Tracked files are digested before and after every check of every run (candidate, obligation, witness), because restoring the candidate's files between runs would otherwise erase the evidence of a check that rewrote them. The cost is one tree digest per check per run.
- `restoreFrom` now removes a path from the index as well as the disk when the tree it restores from lacks the path; the tree recheck found that an index entry outlived its file after a witness run of a refactor.
- `replay` compares states, regression, every check's result and test lists, every requirement status and the lockfile digests. It reruns with the request's own checks and the base's declared ones, and with the recorded image.
- Mutants' Python syntax is checked with the host's `python3`, since a checkout's `.venv` may hold the container's Linux binaries.
- The tamper suite runs on the host by default (`SWARM_TAMPER_ISOLATION=isolated` runs it in containers) so it measures the verifier's judgment apart from the isolation it adds.
- Gates now need a docker daemon for the isolated integration tests; isolated is the default execution, so a test suite that skipped it would not test the product.
- On macOS and Windows, container runs are spaced at least 1.5 s apart, measured from the end of one to the start of the next. colima's virtiofs share keeps a file's entry for about a second, so a file the host replaced just before a container started read as missing (measured: stale up to 0.8 s after the change, never from 1.0 s; this made `npm ci` find no package.json after `git apply`, and the judge read as missing). Every host-side change to the checkout happens between runs, so spacing the runs covers them all; Linux shares no VM filesystem and does not wait.
- A package an npm lockfile installs from outside the repository (`file:../sibling/pkg`, recorded as a `../` key in `packages`) is copied from beside the request's repository into the same place beside the checkout, without its host-built node_modules, and its production dependencies are installed from its own lockfile in the same dependency stage. Its content digest joins the lockfile digests as `local:<path>`. A path that would leave the scratch directory, or a source that is not there, blocks the run. Found on dossier, whose tests import `@ironroot/core` from `../ironroot/packages/core-ts`.
- Dependency preparation moved from checks.ts to prepare.ts.

## 2026-11-01: naming evidence as runners print it

- Test ids from jest, vitest and mocha join suites to the title with ` > `, as the junit reader already did, so one test reads the same whichever report it came from. vitest's and jest's ids come from `ancestorTitles` and `title`; mocha's report holds only `fullTitle` and the test's own `title`, so its suites stay joined by spaces and only the boundary before the title is certain. Ids recorded before this change do not compare with ids recorded after it; no release carried the old ids since 2.0.0 is unpublished.
- A requirement's test name selects a test when its ` > ` parts are a contiguous run of the test's suite path and title. A name that is a substring of a title, or skips a level, selects nothing. Found when a local model named `walkRepo > skips extra directories` and the requirement stayed unverified with the test passing.
- A requirement citing a check that did not run, or a test name that matched nothing, gets a next action naming the checks that ran or the shape of a test path, in place of "run a check that exercises it". A check stays only one the project or the request declares; a command the agent ran is not a check.

## 2026-11-01: authorized behavior changes, end to end

- `verify()` passes the request's `policy.behaviorChange` to the judgment; it was dropped at the API boundary, so no request could authorize a change and `--authorize-behavior-change` did nothing. Found while adding an end-to-end acceptance case for an approved behavior change; only a unit test of `compareRuns` exercised the authorized path before.
- A superseded test's status after the change is its rewritten version's (and before, the witness run's), not the failing old expectation's: the authorized new version replaces the obligation.
- The rule for a check that exits worse with no failing test fires only where the run's report has no failing test, for the obligation run and the candidate's own. A superseded expectation fails in the obligation run by design and explains its exit.
- The predicate records `policy.behaviorChange`, and replay reruns under it; without it a replay of an authorized run would judge the rewrite as unauthorized and diverge.
- A requirement with no mapped evidence gets a next action naming, by title, up to eight tests the executed results show witnessing the change. This names, it does not map: the requirement stays unverified until the producer maps evidence. Found on an acceptance run where a local model added three witnessing tests, never mapped them, and spent its remaining steps elsewhere.

## 2026-11-01: what a cached base run may stand for

- A cached base run is keyed on a digest of the verifier's own code (non-test source, or the built files), with the base commit, the environment and the sealed set. The version string did not change between builds that read reports differently: an acceptance run reused a base read under the old test ids, and every one of its 98 tests read as a new failure. Caches written by other code are left on disk and never read.
- `replay` measures the base afresh, through a call option the public API now carries (`freshBase`), and does not read the cache; the fresh run is still written to it. A replay that reads the base it is checking is not independent: the same acceptance run's replay agreed with the false regressions.
- A failed structure claim says why: the path is a directory, there is no file, or the file lacks the text. An unverified requirement's next action also names, by title, up to eight witnessing tests it does not map, whatever else it maps. Both from the crossfire acceptance run, where the producer's claims named directories and its two witnessing tests went unmapped through two verifications (session 20261101T021508-a9fb2e).
- A requirement's named check holds when its result is `inherited-failures`, as when it is `pass`: the check shows the change broke nothing it measures. It was read as unobserved, so on crossfire, where one unrelated em-dash test fails at both commits, the requirement naming `test` stayed unverified through four verifications with its two witness tests mapped (session 20261101T023752-7721a4). `verify.mjs` holds the same set; a mismatch there reads a correct result as tampered.
- A requirement may name a test with its file first, as runners print it, or by its id (`file::title`); the file narrows the match like the selector's own `file`. From crossfire (session 20261101T033749-e1498f), where six tests named file-first matched nothing.
- `npm ci` in the dependency stage runs with `--foreground-scripts`, for the repository and its local packages. Parallel install scripts raced: ruleprobe's three tree-sitter grammars build with node-gyp in the pinned node:24 image, and `npm ci` failed six times in seven with `make: No rule to make target ... node_addon_api_except.stamp`, at the host-mirrored path and at /w alike, and passed three times in three with the flag. A slower install is the cost of a reproducible one.
- A failed dependency stage blocks with a reason that names the step: fix the dependency the setup output names, or verify with the workspace's installed dependencies (on the host, or `dependencies: linked`), reported as not reproducible. From resident (session 20261101T043359-00df4a), whose lockfile installs on the host only from a cached wheel.
- Every container run of a Node image installs a corepack shim for pnpm in the run's private home (`$HOME/.swarm-bin`, first on PATH) before running the declared command as written. depose's checks (`pnpm run test` and the rest) exited 127 in isolation because the image has corepack but no pnpm (session 20261101T053337-79ac08). The pnpm version is the one the manifest pins, fetched while dependencies are prepared and read from the home's corepack cache with the network closed. Yarn gets no shim: the image ships yarn classic, which a shim would shadow.
- A sandbox's first container run waits the whole shared-filesystem settle time (1.5 s on macOS and Windows), not only runs after the first: docker reported the just-created scratch directory missing once.
- A Python project that measures coverage itself (pytest-cov in its pytest options, or coverage.py `parallel` in pyproject.toml, .coveragerc, setup.cfg or tox.ini) has its tests run as declared and changed-line coverage reported unmeasured with that reason. Wrapping tracemantle's candidate run in `coverage run --append` made coverage refuse to start ("Can't append to data files in parallel mode"), so the candidate's tests never ran (session 20261101T055541-5d24f7). Coverage is a diagnostic; it never decides whether a check ran.
- A package claim's version may be a range written with `x` (`9.x`, `9.6.x`, or a bare `9`), and a resolved version outside the claim is a failing outcome, not an unobserved one: the candidate contradicts what the requirement states. From claimcheck, where the task allowed "the latest 9.x" and two runs delivered 10.1.1 as complete (sessions 20261101T064120-2e5241, 20261101T070045-66c4ac). The verifier still reads no prose: the producer must write the range into its claim.
- A requirement may name a test file alone (a name ending in a source extension) to select every test in it, as the selector's `file` field does. From dependency-detector (session 20261101T071612-d8e2dd), where nine test files named this way matched nothing.
- An upgrade with no package claim is told to name the package with its resolved version, or, where no package version changes, to record the requirement as kind other with its structure and checks. The upgrade rule itself is unchanged: an upgrade needs a package that moved. From quantproof (session 20261101T072642-9b0cb5), whose Node 24 change touched no package version.
- A requirement's test name equal to a test's id selects that test, before any splitting into file and title. pytest ids are `classname::name` with a dotted classname, which is no path, so the ids the verifier prints in its own reasons selected nothing. From dependency-detector (session 20261101T084321-1087ff).
- Before the change is applied, an untracked file the patch creates is removed from the base checkout: the patch is taken against the base commit, so such a file can only be a by-product of the base's own run, and the candidate's version is the one judged. Tracked files are never touched, so a real conflict still refuses the change. From tracemantle (session 20261101T125501-97efc9), where the isolated preparation's `uv lock` wrote uv.lock and the candidate added its own.
- With no check run against the candidate, the regression is unresolved rather than none: nothing is known either way. The same run had reported "regression none".
- Untracked and ignored paths the base's checks write (build output, caches) are removed before the change is applied, so the candidate runs on the base commit with the prepared dependencies, as the base did. The unit is the path git lists with `ls-files --others --directory`: writes inside a directory that existed before the base run stay. From depose (session 20261101T154330-6eee82), where a run that changed nothing was reported with 14 new failures: the base's `build` check had written the workspace packages' output, which 14 test files import and could not load at the base. Whether a candidate saw that output also depended on whether the base came from the cache, so results differed between a cached run and its replay.
- Every list of test ids in a statement is sorted before it is capped at a hundred, and a replay compares those lists as sets. A runner's order is not part of the verdict: on depose (session 20261101T155037-25f560) the replay found the same 17 inherited failures in another order and reported a divergence, and above a hundred ids the kept ones depended on that order.
- Product acceptance closed on 2026-11-01. The verifier defects it found are fixed above: test names and ids, inherited-failure checks, base caching keyed on the verifier's code, native build races, pnpm in the container, self-measuring coverage, version ranges, files the base run leaves, and the order of test ids. The swarm-orchestrator repository keeps the runs under docs/acceptance/2026-10-31/.
- Release preparation, 2026-11-01: CI runs `npm run gates` and a v* tag publishes after the same gates, which now install the packed tarball into a fresh prefix and verify a change through it. The Action takes `authorize-behavior-change`; `verify` and `ci` name it in their help. 2.0.0 folds the unpublished 2026-10-29 notes. The release workflow needs an `NPM_TOKEN` secret in this repository, which it did not have before.
- Attribution trailers removed from the commits this branch adds to `main`, 2026-11-01: the history merge brought 98 commits with `Co-Authored-By` and 39 `Claude-Session` lines. `git filter-repo --refs origin/main..recovery/2026-10-31` dropped those lines and changed nothing else (the head's tree is 93c6b864c before and after; the old head was 1e5c0f3). The 16 in `main`'s own history stay: rewriting them would cut the branch off from `main` and from the published `v1` tag.
- A requirement carries the version constraints the user's own wording states (`versions`: package, ecosystem, range, whether the latest is asked for, and the words), set by the producer's code and never by a model. Each is judged against the candidate's lockfile: within the range holds, outside it fails; with the latest asked for, the registry's latest release within the range is read while dependencies are prepared, the stage with the network open, and only that version holds. A latest that cannot be read leaves the requirement unverified with the reason. Ranges are the forms a task names (1.2.3, 9, 9.x, 9.6.x, ^9.6.1, ~9.6); anything else is refused when the request is parsed. From claimcheck, where "the latest 9.x" was delivered as Stryker 10.1.1 and reported complete twice (sessions 20261101T064120-2e5241, 20261101T070045-66c4ac): the model's own claim named 10.1.1, and a claim is the model's. Removal condition: none; this is the obligation the user stated.

## 2026-11-01: flaky tests are uncertainty

- A test whose failing first run decides its verdict (a new failure, a rewritten expectation, a failing added test, a fix at the base, a witness against the base's source) is run again on the same snapshot, up to `policy.reruns` times (three unless the request says otherwise, ten at most), and is `flaky` once a rerun passes. Nothing else is rerun, since each rerun costs a whole check run; an inherited failure would read the same whatever a rerun showed. From tracemantle (session 20261101T150922-f837ff), whose recorded verification had `test_malformed_history_blocks_final_gate[bundle_sha256]` failing and `[configuration_sha256]` passing where its replay, on the same snapshot, had both failing.
- A flaky test is never a regression and never a fix or a witness. Its check is `unresolved`, the regression is `unresolved` and names it under `flaky`, and a requirement mapped to it is `unverified`. Unresolved rather than none or found: a test whose outcome changes on one snapshot says nothing about the change either way, so found would charge the candidate with the test's nondeterminism and none would credit it with a comparison that was never made. A test failing on every run keeps its verdict, and its runs are recorded too.
- Reruns at the base and against the base's source come after every candidate run (the mutation pass and the held-out checks included). Where the candidate installed its own dependencies, the base's are installed again first, so a base rerun runs on the base's environment; nothing runs on the candidate after them. An install that fails there is an execution problem, so the result cannot be complete on the fixes it leaves.
- verify.mjs does not accept `complete` over a check that records a flaky test.
- A replay compares flaky tests as their own set. Flaky in both runs agrees, whatever each run's sequence of results; flaky in one run and not the other is one divergence that names the test, its runs, and where the other run put it, and the test is left out of the other lists' comparison, so one nondeterministic test is not reported once per list it moved between. A recording made without reruns says so in that line, since one failing run decided it there; such a recording is replayed with the default reruns. tracemantle's replay is the case: `[configuration_sha256]`, preserved in the recording, failed in the replay.

## 2026-11-01: a replay runs as the recording ran

- A replay runs under the recorded execution: a host recording on the host, an isolated one in a container from the recorded image, each with its dependencies prepared fresh as the recording did (`prepared` and `setup` prepare, `none` prepares nothing). From ruleprobe (docs/acceptance/2026-10-31/t3-ruleprobe in swarm-orchestrator): verified on the host on darwin-arm64, its replay always ran in a Linux container and diverged in state and in every test list.
- A host recording replays only on the platform it recorded. `environment.platform` already holds the os and architecture of a host run (`darwin-arm64`), so the statement needs nothing new; a replay elsewhere is refused with both platforms named rather than run, since its divergences would describe the machine and not the change. The execution mode is compared like the state.
- A recording on linked dependencies is refused rather than replayed on whatever is linked now: the installed tree it ran on is gone, so agreement would show nothing and divergence would be noise. A refused replay exits 5, as one that could not run does.
- Closing the acceptance run's defects, 2026-11-01: version constraints from the wording, flaky tests kept as uncertainty with bounded reruns, replay under the recorded execution, and per-process test fixtures each landed with a test that failed before. The version stays 2.0.0: it is unpublished, so the fixes fold into it.
- An unobserved package claim gets a next action of its own: the claim holds where the candidate's lockfile resolves the package to a version the base did not, so drop the claim for a package that did not change or correct it, with what each resolved to. On claimcheck (session 20261101T213431-7eaedd) the task allowed Stryker "to the latest 9.x", which it already was; the model claimed 9.6.1 as an upgrade, the claim held nothing, and the next action read "run a check that exercises it" until the step budget ran out. A constraint from the task's own wording is never offered for dropping.
- Acceptance closed after the fixes, 2026-11-01: the tamper evaluation on the release candidate (0e21ae0) flags 0 of 20 honest patches and 24 of 24 cheats; a ruleprobe verification recorded on the macOS host replays there in agreement; claimcheck's "latest 9.x" is held against the registry's latest within the range. swarm-orchestrator's docs/acceptance/2026-10-31/README.md has the runs.
- Release readiness, 2026-11-01: 2.0.0 at 5d36afd packs to the same bytes from the work tree and from a fresh clone (sha512-xynz5IZq...H0Zg==), the integrity swarm-orchestrator 16.0.0 pins. main is unchanged since 7132869 and is an ancestor of this branch, so it moves here by fast-forward.

It ran on every `v*` tag, so pushing the `v2` Action alias started a release that ran the gates and then refused on the tag check, a red run on every alias move (run 41370691236). ## 2026-11-02: 2.0.1, a refused preparation is recorded as refused

- A dependency preparation that cannot start (a lockfile package from beside the repository that is not there) is its own outcome, `refused`, in `execution.dependencies.mode` and `environment.dependencies`, with the reason in the note. It was `none`, the same as a run that asked for nothing, so a replay prepared nothing, ran the checks without dependencies and diverged (orchestrator session 20261102T210229-519ea0). Replay prepares again for every mode but `none` and meets the same refusal. This adds a value to a signed field, which a reader pinned to 2.0.0's schema rejects; swarm-orchestrator pins swarm-verify exactly, and a 2.0.0 statement keeps `none` and replays as it did.
- With checks declared and the base not measured because preparation was refused or failed, the baseline says so. It said "no checks are declared", false of the dossier repository it was seen on.

## 2026-11-02: 2.0.1, what the acceptance follow-ups found

- The judge finishes in a process a signal ends: SIGTERM, SIGINT and SIGHUP write its end line, then the signal is raised again where nothing else listens, so the process still ends by it. vitest's forks pool ends its workers with SIGTERM, and a held-out vitest check called 29 of depose's 32 processes unchecked and failed whatever its tests did (orchestrator patch release, depose 09b01c1).
- A worker thread the judge starts in is marked as one. A runner that terminates it runs nothing in the thread, so its end is never written; such a thread is counted as unchecked and named among the unmeasured reasons, not as tampering. A thread that changes an assertion is still caught. Claimcheck's vitest 1 held-out check had 28 thread starts with no end.
- `SWARM_HOME` is resolved to an absolute path before use; a relative one had the sealed store looked up from inside the checkout, and the result then said no held-out checks were sealed when a sealed set existed. Where one exists and did not run, the result says that instead.
- A deleted test file and an added one that git pairs as a rename, with more than imports changed, are moved and edited (`testFiles.movedAndEdited`): the base's version runs at its old path against the candidate's source with the moved copy out of that run, and each test is judged as rewritten in place. Read as a deletion, a correct move that also fixed a fixture path had 18 tests "gone" and its base-tests run held both copies, which broke the project's own test count (tracemantle, the orchestrator's t6 comparison). Rename pairing is git's (`diff -M`, its default similarity): a pair it does not see stays a deletion and an addition. The field reads as empty in a 2.0.0 statement.
- The mutation pass blanks string literals and comments over the whole file, not line by line, so an operator inside a docstring, a template literal or a block comment is never mutated. The one mutant of that t6 patch changed "and" to "or" in a docstring and was reported as surviving.

## 2026-11-05: 2.1.0, independent evidence

- The rule is on decisive evidence, not on any evidence: a pre-existing `npm test` passing shows nothing regressed, not that a feature exists, so a passing declared check is never the independent witness of a fix or feature. Decisive by kind: fix and feature, a witnessing test; refactor, structure or a witnessing sealed test; upgrade, a package or a version constraint; other, anything that holds.
- `self-attested` is carried in a new `witness` field beside an `unverified` status, not as a fifth status, so statements stay readable by every 2.x consumer's status enum; the overall state stays `incomplete` with the reason `independent evidence missing: <id> is self-attested`.
- Producer-written checks are a sealed set in the existing store, not a second mechanism: the same overlay, judge and base run as a person's held-out set, told apart by the set's `authority`.
- Claims default to `user-acceptance` because a caller who writes a requirements file is the person accepting the work; a producer passing on its model's claims must say so, and the orchestrator does.
- Package claims and version constraints used `authority` to tell themselves apart; they now differ by shape (`isConstraint`), since both can be the caller's.
- The three pending branches (`fix/container-user-entry`, `fix/version-claim-ranges`, `fix/structure-text-absent`) were merged into `release/2.1.0` first; their changelog entries stand as written.
